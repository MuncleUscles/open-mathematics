# Protocol and trust boundaries

GitHub Pages serves a static dashboard and agent guide. GitHub Actions is a restartable trusted worker. The GenLayer Intelligent Contract is authoritative for decisions and points. No always-on custom backend is required for this pilot. Launch should add a rebuildable read-only indexer, reliable queue/keepers and independent service operators; none may manufacture verdicts.

`protocol` is the reviewed application/default branch. `research` is PR-only, protected with no bypass and strict required Lean/finalized checks bound to the GitHub Actions app. `site` publishes the dashboard. `evidence` is a public report cache, not authority. V1 main and contract history remain visible. V2 carries one frozen, finalized 400-point legacy record into a replacement ledger; consumers must not sum v1 and v2 balances.

1. A contributor commits exactly one enrolled proof and one new normalized JSON record in a single commit directly on canonical research. EIP-191 signing binds wallet, origin, chain, contract, policy, repo/PR, branch/base/head, record path/hash, nonce and expiry. An unedited PR-author comment anchors the signature's freshness; delayed queue execution uses the comment creation time. Replay uses the same stable record ID and cannot credit twice.
2. Trusted workflow code fetches immutable Git objects, compares complete trees, checks the actual canonical ref independently of cached PR metadata, recovers the wallet and validates the record. It never checks out or executes PR-controlled code. The proof is inserted into trusted definitions and a tiny syntax policy, then checked using pinned Lean 4.19.0 and a checksum-pinned container, no network, no credentials, restricted resources and axioms. A green CI badge is insufficient.
3. Exact settled dependencies are loaded from finalized IC records and canonical merge commits. Their credited artifact is reconstructed and hash-checked. Trusted Lean expression inspection checks surviving constant references after beta, zeta and projection reduction, with theorem bodies opaque. This establishes structural use, not mathematical necessity. Imported names, citations and unused arguments are insufficient.
4. The verifier signs evidence, including the immutable record, actual GitHub author ID, pinned statement, proof artifact and verified dependencies. Only its enrolled IC identity can register. Independent GenLayer validators judge bounded untrusted evidence; numerical award bands and recipient vectors must agree. Output shape, bounds and references are validated. Prompt injection and semantic novelty are not solved perfectly by an LLM; conservative decisions and public challenge windows are essential.
5. The application challenge window and native finality both complete. Up to two challenge rounds may block and revise judgment. The worker validates successful FINALIZED receipts, exact contract/calldata, current round and independent validator agreement. CI does not decide merit.
6. The bot rechecks protection, canonical base and PR head, publishes the contract decision check and requests an exact-head merge. GitHub's merge API does not atomically pin a base: strict up-to-date protection, serialized worker execution and prechecks mitigate that race. Both actual merge parents and canonical ancestry are verified before the executor confirms merge on the IC. A discrepancy stops credit. An executor-attested stale unmerged record expires and releases its statement reservation; credited work can never be released. Only merge commits are supported.
7. Initial points credit once. The enrolled executor alone requests adjudication and impact review, finalizes, and settles after independently checking non-leader-only finalized receipts. Review/finalize/settle calls include the exact challenge round, so a previous receipt cannot be reused for a new round. Later-impact review takes only a settled downstream ID and its round. Recipients come from immutable, verified earlier dependencies; the caller cannot select a score or wallet. Same-wallet credit is excluded, a pool of at most min(300, initial downstream points) is allocated in 100-point bands, reasons are public, a separate challenge window applies, and settlement is idempotent. No recursive cascade. Another wallet or the same GitHub author's activity does not establish independent human identity.

If a contributor edits or deletes the original signed comment after registration, automatic recovery stops. The enrolled executor can release an affected unmerged decision after checking the archived claim and current GitHub state.

Limits: 100 registered records, 1,000,000 total points, two application challenges each; controlled trials must not exhaust the registry. Two throwaway challenges can consume the bounded application challenge slots; wallets alone cannot prevent this abuse. The verifier and executor are trusted roles. Their dedicated keys are encrypted repository secrets, isolated from contributor execution. Both checks currently use GitHub Actions app15368, not independent GitHub Apps. Repository administrators, trusted workflows, pinned images, GenLayer availability and these operator keys remain explicit trust roots. Arbitrary proof programs, a complete P/NP formalization, production Sybil resistance, global novelty verification and testnet deployment are not implemented.

Migration trust: the one historical record is imported by the existing trusted verifier, with its exact public snapshot hash hardcoded in the contract. The bootstrap re-reads finalized v1 state and checks the original merge-confirmation receipt. No amount or recipient can be changed. This is a verifier-attested migration, not an on-chain cross-contract proof. The initial Studio cross-contract attempt timed out after 600 seconds; its unactivated address and failed transaction are retained in the migration report.
