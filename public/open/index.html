The flagship question · Still open

P vs NP

P ? NP

Read the problem at Clay Mathematics Institute

Easy to check.
Easy to find?

If a solution can be checked efficiently, can it also be found efficiently? That is the question behind P versus NP. We do not know the answer.

This is a place to work toward either answer, one useful result at a time. A small theorem is not a solution to the whole problem. A failed approach can still teach us something.

More useful work. More shared credit. A formal result has one fixed budget: 80% goes to its author first; 20% is reserved for meaningful use of earlier work. Any unused reserve returns to the author. More accounts do not create a bigger budget.

Points are nontransferable research records. There is no token, bridge, trading or promised financial value. Correctness alone does not guarantee points.

A proof is not a verdict.

Lean checks a submitted theorem, including its definitions and permitted assumptions. GenLayer decides whether the work is useful. The GitHub bot implements that decision through the protected branch.

Finality is not always agreement.

A review can exhaust its consensus rotations without an agreed outcome. That does not authorize a merge or points. Unresolved work cannot be resubmitted for another draw.

Current proof format, challenges & pilot limits

The reviewed problem policy specifies the pinned Lean environment and accepted proof format. Research notes are explicitly nonformal. There is no enrolled canonical full P-versus-NP theorem; each proof establishes its exact submitted statement.

The application challenge window is five minutes. Up to two evidence-backed application challenges can pause a decision for independent review before settlement. Native appeals are separate. Settled points do not yet have a correction mechanism.

Retrospective credit currently covers verified direct formal proof use. Citation-only influence, general semantic graph relationships and cross-ledger rewards are not automated. A positive live downstream point award and the full application challenge flow remain to be demonstrated.

The PR author must post the exact wallet-signed claim in an unedited comment. The verifier matches GitHub account IDs and verifies the wallet signature. GitHub usernames are separately verified and recorded on chain. Account age and one active claim per GitHub author provide basic spam controls. They do not establish independent humans or complete Sybil resistance. Duplicate checks are bounded, not a comprehensive literature review. The pilot trusts reviewed verifier and executor roles and repository administration.

This is a static site backed by native ledger reads and GitHub Actions. Published snapshots are dated, limited to the newest twelve records, and cannot authorize merges or points. Live reads are collected over an interval, not as an atomic snapshot.
